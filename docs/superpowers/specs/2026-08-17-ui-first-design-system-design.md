# Omninode UI 우선 전환 설계

## 1. 목적

기능별 수직 슬라이스 진행과 별개로, Omninode의 화면을 먼저 일관된 관리 도구 UI로 전환한다. 이 단계의 목표는 실제 API·DB 동작을 추가하는 것이 아니라 모든 대상 라우트에 레이아웃, 화면 구조, 상태 표현, 상호작용 모양을 갖춘 UI를 제공하는 것이다.

`TODO.md`는 기존처럼 기능·API·권한·DB 완료의 단일 기준으로 유지한다. UI 전환 상태는 별도 UI 진행표에서 관리해 화면 완성과 기능 완성을 혼동하지 않는다.

## 2. 범위

현재 라우트 61개 중 다음 3개는 UI 전환 대상에서 제외한다.

- `/`: `/docs`로 이동하는 리디렉션 전용 경로
- `/about`: 전역 소개 화면을 제공하지 않는다는 제품 결정에 따른 비대상 경로
- `/settings`: 전역 설정 화면을 제공하지 않는다는 제품 결정에 따른 비대상 경로

따라서 UI 전환 대상은 58개 라우트다. 기존 URL과 도메인 정책은 유지하며, URL 변경이나 API 계약 변경은 이 설계의 범위가 아니다.

## 3. 디자인 원칙

- 현대적인 전문 위키·설정 관리 도구를 기준으로 한다.
- 밝은 중립 배경(`slate-50` 계열), 흰 표면, 얇은 경계선, 낮은 그림자를 사용한다.
- 주조색은 `blue-600`, hover는 `blue-700`, 선택 배경은 `blue-50`으로 통일한다.
- 제목은 `slate-900`, 본문은 `slate-700`, 보조 정보는 `slate-500`을 기준으로 한다.
- 공개·활성, 초안·보관, 비공개, 숨김·삭제·위험 상태는 각각 semantic color와 텍스트 Badge를 함께 사용한다.
- 판타지 장식과 과도한 카드 사용은 배제한다. 관리 화면은 테이블·트리·보조 패널을 사용해 정보 밀도를 유지한다.
- 동일한 기능은 모든 화면에서 동일한 필터, 상태, 메뉴, 저장·취소·삭제 패턴을 사용한다.

## 4. 레이아웃 체계

화면은 기능명이 아니라 사용자의 작업 맥락에 따라 다음 6개 레이아웃으로 구성한다.

| 레이아웃 | 대상 | 역할 |
| --- | --- | --- |
| 문서 목록 (`default`) | `/docs`, 문서 목록, 문서 상세 | 카테고리 기반 탐색과 읽기 중심의 문서 경험 |
| 문서 편집 | 문서 생성·수정 | 목차, 편집 상태, 명시적 저장과 편집 보조 도구 |
| 슈퍼 어드민 대시보드 | `/admin`, 전역 관리자 관리 | 시스템 전역 KPI와 프로젝트·월드·문서·관리자 관리 |
| 프로젝트 대시보드 | 프로젝트 하위 관리 화면 | 프로젝트 범위의 월드·문서·관리자·설정 관리 |
| 월드 대시보드 | 월드 하위 관리 화면 | 월드 범위의 문서·카테고리·템플릿·관계·파생 탐색 관리 |
| 인증 | 로그인, 계정, 비밀번호 변경, 권한 요청 | 사이드바 없는 집중형 계정 흐름 |

카테고리, 템플릿, 관계, 관리자, 설정은 별도 레이아웃을 만들지 않는다. 각 기능은 상위 범위의 프로젝트 또는 월드 대시보드 안에서 사이드바 메뉴와 작업 뷰로 열린다.

문서 상세는 문서 목록에서 이어지는 읽기 흐름이므로 문서 목록 레이아웃을 공유한다. 문서 생성과 수정은 하나의 문서 편집 레이아웃을 공유한다.

## 5. 공통 셸과 탐색

### 상단바

- 로고, 사이드바 제어, 현재 범위 Context Selector, 전역 또는 범위 검색, 알림, 도움말, 계정 영역으로 구성한다.
- 비로그인 공개 문서 화면에는 `관리자 로그인` 버튼을 표시한다.
- 로그인 후에는 관리자 이름·이메일·역할과 계정 메뉴를 표시한다.
- Context Selector는 슈퍼 어드민·프로젝트·월드 범위를 명확히 구분한다.

### 사이드바

- 문서 목록 레이아웃은 카테고리 트리와 현재 문서 위치를 중심으로 한다.
- 슈퍼 어드민 대시보드는 대시보드, 프로젝트, 월드, 문서, 카테고리, 템플릿, 관리자를 제공한다.
- 프로젝트 대시보드는 프로젝트 대시보드, 월드, 문서, 카테고리, 템플릿, 관리자, 설정을 제공한다.
- 월드 대시보드는 월드 대시보드, 문서, 카테고리, 템플릿, 관계, 파생 탐색을 제공한다.
- 전역 홈과 소개 메뉴는 만들지 않는다.

## 6. 공통 컴포넌트

### 정보·탐색

- KPI 카드, 페이지 헤더, Breadcrumb, Context Selector, 검색·필터 바, 데이터 테이블, 페이지네이션
- 카테고리·템플릿·섹션 트리, 문서 목차, 우측 정보 패널, 최근 활동, 빠른 작업, 상태 Badge
- 로딩, 빈 상태, 오류 상태, 권한 없음 상태, 삭제 확인 다이얼로그

### 폼

Element Plus를 기반으로 공통 래퍼와 스타일 규칙을 만든다.

- `ElForm`, `ElInput`, `ElInputNumber`, `ElSelect`, `ElTreeSelect`, `ElDatePicker`
- `ElSwitch`, `ElCheckbox`, `ElRadioGroup`, `ElUpload`, `ElDialog`
- 텍스트·이메일·비밀번호·검색·숫자·다중 행 입력과 단일/다중/계층 선택
- 섹션 헤더, 레이블, 필수 표기, 도움말, 유효성 오류, 읽기 전용 값, 위험 작업 영역
- 기본 저장, 보조 취소, 위험 삭제를 일관된 액션 계층으로 표현
- 저장 중·성공·오류·확인 상태는 UI로 표시하지만 이 단계에서 API를 호출하지 않는다.

## 7. 관계형 fixture

더미 데이터는 페이지마다 독립된 임의 데이터가 아니라 하나의 도메인 관계를 공유하는 UI 전용 fixture다.

- 프로젝트 3개와 프로젝트별 월드 2~4개
- 월드별 3단계 카테고리 트리, 템플릿, 문서, 관계 타입, 관계
- SUPER_ADMIN을 포함한 관리자 4명과 프로젝트별 역할·권한 표현
- 공개, 비공개, 초안, 숨김, 삭제 상태를 가진 문서
- 최근 활동, 즐겨찾기, 검색 결과, 휴지통이 같은 문서를 참조

fixture는 실제 API를 대체하거나 서버 상태를 변경하지 않는다. 실제 기능을 연결하는 단계에서는 fixture 공급자를 Vue Query 결과로 교체하고 화면 컴포넌트 구조는 유지한다.

## 9. UI 전용 진행표

구현 계획에서 `docs/UI-DESIGN-TODO.md`를 만든다. 각 항목은 다음을 기록한다.

- 대상 라우트
- 적용 레이아웃
- 사용 공통 컴포넌트
- 필요한 fixture
- 기본·로딩·빈·오류·권한 없음 상태
- UI 상호작용 범위
- 검증 결과

이 문서는 UI 전환의 진행표이며 기존 `TODO.md`를 대체하지 않는다.

## 10. 완료 기준과 검증

각 UI 묶음은 다음을 충족해야 완료로 표시한다.

- 대상 라우트가 지정된 레이아웃과 fixture를 사용해 렌더링한다.
- 공통 탐색, Context, 사이드바, 상태 표현이 화면군 안에서 일관된다.
- 목록, 로딩, 빈, 오류, 권한 없음의 표시가 있다.
- 폼은 입력, 유효성 표시, 저장 중, 취소, 위험 작업의 시각 상태를 제공한다.
- 버튼, 필터, 탭, 다이얼로그는 UI 상호작용만 제공하며 API를 호출하지 않는다.
- 데스크톱 우선 레이아웃을 제공하며, 태블릿·모바일에서는 사이드바와 보조 패널을 접는다.
- 영향 범위에 맞는 컴포넌트 테스트, `pnpm lint`, `pnpm exec vue-tsc --noEmit`, `pnpm build`를 실행한다.

## 11. 비범위

- 실제 API 호출, DB 스키마·마이그레이션, 권한 판정 로직 변경
- URL 변경, 도메인 정책 변경, 기존 기능 TODO의 완료 처리
- 자동 저장, 신규 리비전·비교·롤백·토론 기능
- `/`, `/about`, `/settings`의 UI 설계 또는 구현
