# 옴니노드 데이터베이스 명세서

## 1. 설계 개요

옴니노드는 하나의 설정 문서를 하나의 **노드(Node)** 로 취급하고, 문서를 작성·분류·연결하는 관계형 세계관 관리 시스템이다.

핵심 기능은 다음 세 가지다.

```text
문서 관리
문서 분류
문서 연결
```

데이터의 주요 소속 범위는 다음과 같이 구분한다.

```text
System
├─ 기본 Category
├─ 기본 Template
└─ 기본 Relationship Type

World
├─ Admin
├─ Project
├─ 사용자 정의 Relationship Type
└─ Relationship
   └─ 같은 World의 여러 Project 문서를 연결

Project
├─ 사용자 정의 Category
├─ 사용자 정의 Template
└─ Document
```

소속 원칙은 다음과 같다.

1. 기본 Category, 기본 Template, 기본 Relationship Type은 시스템 전역 데이터다.
2. 사용자 정의 Category와 사용자 정의 Template은 Project 종속 데이터다.
3. 사용자 정의 Relationship Type과 실제 Relationship은 World 종속 데이터다.
4. Document는 Project 종속 데이터다.
5. 같은 World에 속한 서로 다른 Project의 Document끼리 Relationship으로 연결할 수 있다.
6. Category와 Template은 서로 할당되지 않은 상태에서도 각각 독립적으로 존재할 수 있다.
7. 기본 Category는 모든 Project에서 직접 사용할 수 있으며 `project_categories`에 매핑하지 않는다.
8. 기본 Template은 시스템 전역에 존재하고, 특정 Project에서 실제 사용하거나 Category에 적용할 때 `project_templates`를 사용한다.

# 2. 공통 컬럼

모든 테이블은 다음 공통 컬럼을 가진다.

| 컬럼 | 타입 | Key | NULL | 설명 |
| --- | --- | --- | :---: | --- |
| `id` | BIGINT | PK | N | 자동 증가 식별자 |
| `useYn` | CHAR(1) | | N | 사용 여부 `Y/N` |
| `delYn` | CHAR(1) | | N | 소프트 삭제 여부 `Y/N` |
| `createId` | BIGINT | FK → `admins.id` | Y | 최초 생성 관리자 |
| `createDate` | TIMESTAMP | | N | 최초 생성 일시 |
| `updateId` | BIGINT | FK → `admins.id` | Y | 최종 수정 관리자 |
| `updateDate` | TIMESTAMP | | Y | 최종 수정 일시 |
| `deleteId` | BIGINT | FK → `admins.id` | Y | 삭제 관리자 |
| `deleteDate` | TIMESTAMP | | Y | 삭제 일시 |

날짜는 DB에서는 날짜/시간 타입으로 관리하고 API 입출력에서는 UTC ISO 8601 형식으로 통일한다.

```text
yyyy-MM-dd'T'HH:mm:ss.SSZ

예:
2026-08-18T01:04:32.15Z
```

상태의 의미는 다음과 같다.

```text
useYn = Y / delYn = N
→ 정상 사용

useYn = N / delYn = N
→ 존재하지만 비활성

delYn = Y
→ 소프트 삭제
```

공통 상태 규칙은 다음과 같다.

1. `useYn`, `delYn`은 `Y/N`만 허용한다.
2. 상위 데이터가 비활성화되거나 삭제되어도 하위 데이터의 `useYn`, `delYn`을 연쇄 변경하지 않는다.
3. 실제 접근 가능 여부는 필요할 경우 상위 경로의 상태까지 함께 판정한다.
4. 삭제는 물리 삭제가 아니라 소프트 삭제를 기본으로 한다.

# 3. 동일명 생성 요청과 복구 정책

생성 요청 시 같은 업무 유일 범위에서 동일한 이름의 데이터가 존재하면 다음과 같이 처리한다.

```text
활성 동일명 존재
→ 중복 오류

삭제 동일명 존재
→ 기존 메인 row를 초기화하여 복구

동일명 없음
→ 신규 생성
```

복구는 과거 상태 전체를 되살리는 행위가 아니다.

```text
메인 row
→ 기존 id 유지
→ 신규 생성 요청값으로 업무 데이터 초기화
→ useYn = Y
→ delYn = N
→ deleteId = NULL
→ deleteDate = NULL
→ updateId / updateDate 갱신
```

감사 컬럼은 다음 원칙을 사용한다.

1. `id`는 기존 값을 유지한다.
2. `createId`, `createDate`는 최초 생성 이력으로 유지한다.
3. 복구 행위는 `updateId`, `updateDate`에 기록한다.
4. `deleteId`, `deleteDate`는 초기화한다.

연관 데이터는 재사용하지 않는다.

```text
기존 연관 데이터
→ useYn = N
→ delYn = Y

신규 구성
→ 새로운 row로 다시 생성
```

예시는 다음과 같다.

```text
Template 복구
→ templates 메인 row 복구
→ 기존 template_headings 전부 useYn=N, delYn=Y
→ 신규 heading 새 row 생성
```

```text
Document 복구
→ documents 메인 row 복구
→ 기존 document_revisions 전부 useYn=N, delYn=Y, currentYn=N
→ 신규 최초 revision 생성
```

```text
Relationship Type 복구
→ relationship_types 메인 row 복구
→ 기존 relationship_roles, relationship_role_categories 폐기
→ 신규 role / category 매핑 재생성
```

# 4. 관리자

## 4.1 `admins`

모든 관리자 계정을 관리한다.

SUPER_ADMIN, ADMIN, SUB_ADMIN은 별도 테이블을 만들지 않고 `role`로 구분한다.

| 컬럼 | 타입 | Key | NULL | 설명 |
| --- | --- | --- | :---: | --- |
| `id` | BIGINT | PK | N | 관리자 ID |
| `email` | VARCHAR | UK | N | 로그인 이메일 |
| `password` | VARCHAR | | N | 비밀번호 해시 |
| `name` | VARCHAR | | N | 관리자 이름 |
| `role` | VARCHAR/ENUM | | N | 관리자 역할 |
| `passwordChangedYn` | CHAR(1) | | N | 최초 비밀번호 변경 완료 여부 |
| 공통 컬럼 | | | | |

### `role`

```text
SUPER_ADMIN
ADMIN
SUB_ADMIN
```

### 제약

```text
UNIQUE(email)
```

### 업무 규칙

1. SUPER_ADMIN은 시스템 전체에서 정확히 1명이다.
2. SUPER_ADMIN은 모든 World와 Project에 접근할 수 있다.
3. ADMIN은 SUPER_ADMIN의 승인으로 생성한다.
4. ADMIN은 World가 하나도 없는 상태로 존재할 수 있다.
5. ADMIN은 권한을 얻은 뒤 직접 World를 생성할 수 있다.
6. ADMIN 생성과 World 소속은 서로 독립된 개념이다.
7. SUB_ADMIN은 ADMIN이 직접 생성한다.
8. ADMIN/SUB_ADMIN은 임시 비밀번호로 생성한다.
9. ADMIN/SUB_ADMIN의 최초 `passwordChangedYn = N`이다.
10. `passwordChangedYn = N`이면 비밀번호 변경 및 로그아웃 외 기능에 접근할 수 없다.
11. 최초 비밀번호 변경 완료 시 `passwordChangedYn = Y`로 변경한다.
12. SUPER_ADMIN은 최초부터 `passwordChangedYn = Y`로 관리한다.
13. 삭제된 계정이라도 이메일은 재사용하지 않는다.

---

## 4.2 `admin_requests`

ADMIN 권한 신청을 관리한다.

| 컬럼 | 타입 | Key | NULL | 설명 |
| --- | --- | --- | :---: | --- |
| `id` | BIGINT | PK | N | 요청 ID |
| `email` | VARCHAR | | N | 신청 이메일 |
| `name` | VARCHAR | | N | 신청자 이름 |
| `status` | VARCHAR/ENUM | | N | 처리 상태 |
| 공통 컬럼 | | | | |

### 상태

```text
PENDING
APPROVED
REJECTED
```

### 업무 규칙

1. 동일 이메일의 과거 거절 요청은 존재할 수 있다.
2. 동일 이메일에 활성 `PENDING` 요청이 두 개 이상 존재해서는 안 된다.
3. 이미 `admins.email`에 존재하는 이메일은 ADMIN 신청을 할 수 없다.
4. 승인 처리는 계정 생성과 요청 상태 변경을 하나의 트랜잭션으로 처리한다.
5. 승인 시 특정 World에 자동 배정하지 않는다.

```text
PENDING
→ SUPER_ADMIN 승인
→ admins 생성(role = ADMIN)
→ 임시 비밀번호 생성
→ passwordChangedYn = N
→ APPROVED
→ 계정 정보 이메일 발송
```

## 4.3 `world_admins`

World와 ADMIN/SUB_ADMIN의 연결을 관리한다.

| 컬럼 | 타입 | Key | NULL | 설명 |
| --- | --- | --- | :---: | --- |
| `id` | BIGINT | PK | N | 매핑 ID |
| `worldId` | BIGINT | FK → `worlds.id` | N | World |
| `adminId` | BIGINT | FK → `admins.id` | N | 관리자 |
| 공통 컬럼 | | | | |

### 제약

```text
UNIQUE(worldId, adminId)
```

### 업무 규칙

1. SUPER_ADMIN은 `world_admins`에 등록하지 않는다.
2. World에는 활성 ADMIN이 정확히 1명 존재해야 한다.
3. SUB_ADMIN은 0명 이상 존재할 수 있다.
4. ADMIN/SUB_ADMIN 구분은 `admins.role`로 판단한다.
5. SUB_ADMIN은 여러 World에 소속될 수 있다.
6. ADMIN은 World 생성 전까지 `world_admins` row가 없어도 된다.
7. ADMIN이 World를 생성하면 해당 ADMIN과 신규 World의 `world_admins` row를 같은 트랜잭션에서 생성한다.

```text
UNIQUE(projectId, adminId)
```

1. 21개 권한은 `Y/N`만 허용한다.
2. ADMIN과 SUPER_ADMIN은 이 테이블을 사용하지 않는다.
3. SUB_ADMIN만 대상이 된다.
4. SUB_ADMIN은 해당 Project가 속한 World의 `world_admins`에 먼저 등록되어 있어야 한다.
5. 활성 `project_admin_permissions`가 없으면 SUB_ADMIN은 해당 Project를 열람할 수 없다.
6. `useYn = N`이면 개별 21개 값을 유지한 채 Project 전체 권한 세트를 비활성화한다.

# 5. World / Project

## 5.1 `worlds`

최상위 세계관 단위다.

| 컬럼 | 타입 | Key | NULL | 설명 |
| --- | --- | --- | :---: | --- |
| `id` | BIGINT | PK | N | World ID |
| `name` | VARCHAR | | N | World명 |
| 공통 컬럼 | | | | |

World 이름은 전역 UNIQUE로 강제하지 않는다.

### 업무 규칙

1. ADMIN이 직접 World를 생성할 수 있다.
2. World 생성 시 생성 ADMIN을 `world_admins`에 연결한다.
3. SUPER_ADMIN은 `world_admins` 매핑 없이 모든 World에 접근한다.

---

## 5.2 `projects`

World 내부의 창작 Project를 관리한다.

| 컬럼 | 타입 | Key | NULL | 설명 |
| --- | --- | --- | :---: | --- |
| `id` | BIGINT | PK | N | Project ID |
| `worldId` | BIGINT | FK → `worlds.id` | N | 소속 World |
| `name` | VARCHAR | | N | Project명 |
| 공통 컬럼 | | | | |

### 제약

활성 Project는 같은 World 안에서 이름이 중복될 수 없다.

```text
UNIQUE(worldId, name)
WHERE delYn = 'N'
```

### 업무 규칙

1. 다른 World에서는 동일한 Project 이름을 사용할 수 있다.
2. 삭제된 동일 이름 Project 생성 요청은 기존 Project 메인 row를 초기화 복구한다.
3. Project는 사용자 정의 Category, 사용자 정의 Template, Document의 소속 범위 기준점이다.

# 6. Category

## 6.1 `categories`

Category 정의를 관리한다.

기본 Category와 사용자 정의 Category를 동일 테이블에서 관리한다.

| 컬럼 | 타입 | Key | NULL | 설명 |
| --- | --- | --- | :---: | --- |
| `id` | BIGINT | PK | N | Category ID |
| `parentId` | BIGINT | FK → `categories.id` | Y | 상위 Category |
| `name` | VARCHAR | | N | Category명 |
| `depth` | SMALLINT | | N | Category 단계 1~3 |
| `defaultYn` | CHAR(1) | | N | 기본 제공 여부 |
| 공통 컬럼 | | | | |

### 기본 / 사용자 정의

```text
defaultYn = Y
→ 시스템 기본 Category
→ 특정 World / Project 소속 없음
→ 수정 / 삭제 불가

defaultYn = N
→ 사용자 정의 Category
→ Project 소속은 project_categories로 판단
```

### 트리 제약

```text
depth = 1
→ parentId = NULL

depth = 2
→ parentId 필수
→ parent.depth = 1

depth = 3
→ parentId 필수
→ parent.depth = 2
```

`depth`는 1~3만 허용한다.

### 업무 규칙

1. Category는 생성 후 `depth`를 변경할 수 없다.
2. Category는 생성 후 `parentId`를 변경할 수 없다.
3. 상향/하향이 필요한 경우 신규 Category를 생성하고 기존 Document를 신규 Category로 이동한다.
4. Category 정렬 순서는 DB에 저장하지 않는다.
5. 기본 Category는 모든 Project에서 직접 사용 가능하다.
6. 기본 Category는 `project_categories`에 매핑하지 않는다.
7. 사용자 정의 Category의 부모는 기본 Category 또는 같은 Project 소속 사용자 정의 Category만 가능하다.
8. 다른 Project의 사용자 정의 Category를 부모로 사용할 수 없다.
9. 같은 World의 Relation 설정에서는 다른 Project의 사용자 정의 Category도 선택 후보로 조회할 수 있다.

---

## 6.2 `project_categories`

사용자 정의 Category와 Project의 소속을 관리한다.

| 컬럼 | 타입 | Key | NULL | 설명 |
| --- | --- | --- | :---: | --- |
| `id` | BIGINT | PK | N | 매핑 ID |
| `projectId` | BIGINT | FK → `projects.id` | N | Project |
| `categoryId` | BIGINT | FK → `categories.id` | N | 사용자 정의 Category |
| 공통 컬럼 | | | | |

### 제약

```text
UNIQUE(projectId, categoryId)
```

활성 사용자 정의 Category는 하나의 Project에만 귀속되어야 한다.

```text
UNIQUE(categoryId)
WHERE delYn = 'N'
```

### 업무 규칙

1. `categoryId`는 `categories.defaultYn = N`인 사용자 정의 Category만 허용한다.
2. 기본 Category는 이 테이블에 매핑하지 않는다.
3. 사용자 정의 Category 생성 시 Category 메인 row와 Project 매핑을 같은 트랜잭션에서 생성한다.
4. 사용자 정의 Category 복구 시 기존 `project_categories` 매핑은 폐기하고 신규 매핑을 생성한다.

## 7.2 `template_headings`

Template의 Markdown Heading 구성을 관리한다.

| 컬럼 | 타입 | Key | NULL | 설명 |
| --- | --- | --- | :---: | --- |
| `id` | BIGINT | PK | N | Heading ID |
| `templateId` | BIGINT | FK → `templates.id` | N | Template |
| `label` | VARCHAR | | N | Heading 라벨 |
| `level` | SMALLINT | | N | H1/H2/H3 |
| `sortOrder` | INTEGER | | N | 출력 순서 |

### 제약

```text
level IN (1, 2, 3)

UNIQUE(templateId, sortOrder)
```

Heading `label` 자체는 중복을 DB 차원에서 제한하지 않는다.

### 복구 규칙

Template 메인 row 복구 시 기존 Heading은 모두 폐기하고 신규 요청을 기준으로 새 row를 생성한다.

---

## 7.3 `project_templates`

Project와 Template의 소속 및 선택적 Category 적용을 관리한다.

| 컬럼 | 타입 | Key | NULL | 설명 |
| --- | --- | --- | :---: | --- |
| `id` | BIGINT | PK | N | 매핑 ID |
| `projectId` | BIGINT | FK → `projects.id` | N | Project |
| `categoryId` | BIGINT | FK → `categories.id` | Y | 적용 대상 1단계 Category, 미할당이면 NULL |
| `templateId` | BIGINT | FK → `templates.id` | N | Template |
| 공통 컬럼 | | | | |

### 의미

```text
categoryId = NULL
→ Template이 Project에는 소속되어 있으나 Category에는 미할당

categoryId != NULL
→ 해당 Project의 1단계 Category에 Template 적용
```

### 제약 및 업무 규칙

1. 사용자 정의 Template은 활성 `project_templates`를 통해 하나의 Project에만 귀속되어야 한다.
2. 기본 Template은 Project 소속 개념이 없지만 실제 Project에 적용할 때 `project_templates`를 사용한다.
3. `categoryId`가 존재하면 반드시 `depth = 1`이어야 한다.
4. 사용자 정의 Category라면 해당 Category가 동일 Project의 `project_categories`에 속해야 한다.
5. 기본 Category는 별도 `project_categories` 매핑 없이 사용할 수 있다.
6. Template 하나를 같은 Project의 여러 Category에서 사용할 수 있다.
7. 사용자 정의 Template의 모든 활성 매핑은 동일 Project를 가리켜야 한다.
8. 사용자 정의 Template이 아무 Category에도 적용되지 않았다면 `categoryId = NULL`인 소속 매핑을 유지한다.
9. Template 복구 시 기존 `project_templates` 매핑은 폐기하고 신규 소속/적용 매핑을 생성한다.

### 권장 제약

사용자 정의 Template의 Project 단일 귀속은 단일 row UNIQUE만으로 완전히 표현하기 어렵기 때문에 DB 제약과 서비스 검증을 함께 사용한다.

# 8. Document

## 8.1 `documents`

실제 설정 문서이며 하나의 Node다.

| 컬럼 | 타입 | Key | NULL | 설명 |
| --- | --- | --- | :---: | --- |
| `id` | BIGINT | PK | N | Document ID |
| `projectId` | BIGINT | FK → `projects.id` | N | Project |
| `title` | VARCHAR | | N | 문서 제목 |
| `categoryId` | BIGINT | FK → `categories.id` | N | 1단계 Category |
| `subCategory1Id` | BIGINT | FK → `categories.id` | Y | 2단계 Category |
| `subCategory2Id` | BIGINT | FK → `categories.id` | Y | 3단계 Category |
| 공통 컬럼 | | | | |

본문은 이 테이블에 저장하지 않는다.

### 제목 제약

제목은 Wiki Link 식별 문자열 역할을 한다.

```text
[[문서 제목]]
```

따라서 생성 후 제목 수정은 허용하지 않는다.

활성 Document 기준:

```text
UNIQUE(projectId, title)
WHERE delYn = 'N'
```

### Category 제약

```text
categoryId
→ depth = 1

subCategory1Id
→ NULL 가능
→ 값이 있으면 depth = 2
→ parentId = categoryId

subCategory2Id
→ NULL 가능
→ 값이 있으면 subCategory1Id 필수
→ depth = 3
→ parentId = subCategory1Id
```

선택 가능한 Category는 다음과 같다.

1. 기본 Category.
2. 해당 Document의 Project에 귀속된 사용자 정의 Category.

다른 Project의 사용자 정의 Category를 문서 분류에 사용할 수 없다.

---

## 8.2 `document_revisions`

Document의 Markdown 본문과 수정 이력을 저장한다.

| 컬럼 | 타입 | Key | NULL | 설명 |
| --- | --- | --- | :---: | --- |
| `id` | BIGINT | PK | N | Revision ID |
| `documentId` | BIGINT | FK → `documents.id` | N | 대상 Document |
| `content` | TEXT | | N | Markdown 본문 |
| `currentYn` | CHAR(1) | | N | 현재 Revision 여부 |
| 공통 컬럼 | | | | |

### 업무 규칙

1. Document 하나에는 활성 현재 Revision이 정확히 하나 존재해야 한다.
2. `content = ''`은 허용한다.
3. `content = NULL`은 허용하지 않는다.

문서 생성:

```text
documents 생성
→ document_revisions 생성
→ currentYn = Y
```

수정:

```text
현재 content와 신규 content 비교
→ 동일: Revision 생성 안 함
→ 다름: 기존 currentYn=N + 신규 Revision currentYn=Y
```

복원:

```text
기존 currentYn = N
복원 대상 currentYn = Y
신규 Revision 생성 안 함
```

동일 제목 삭제 Document를 생성 요청으로 복구하는 경우:

```text
documents 메인 row 복구
→ 기존 document_revisions 전부 useYn=N, delYn=Y, currentYn=N
→ 신규 최초 Revision 생성
→ currentYn=Y
```

# 9. Relationship 정의

## 9.1 `relationship_types`

기본 Relationship Type과 World 사용자 정의 Relationship Type을 관리한다.

| 컬럼 | 타입 | Key | NULL | 설명 |
| --- | --- | --- | :---: | --- |
| `id` | BIGINT | PK | N | Relationship Type ID |
| `worldId` | BIGINT | FK → `worlds.id` | Y | 사용자 정의 관계 소속 World |
| `name` | VARCHAR | | N | 정방향 관계명 |

| `displayTemplate` | TEXT | | N | 자연어 표시 Template |
| `defaultYn` | CHAR(1) | | N | 기본 제공 여부 |
| 공통 컬럼 | | | | |

### 기본 Relationship Type

```text
defaultYn = Y
→ worldId = NULL
→ 시스템 전역
→ 수정 불가
→ 삭제 불가
```

### 사용자 정의 Relationship Type

```text
defaultYn = N
→ worldId 필수
→ World 종속
```

### 방향 유형

```text
DIRECTED
SYMMETRIC
```

`DIRECTED`라고 해서 반드시 `reverseName`이 존재해야 하는 것은 아니다.

### 업무 규칙

1. 사용자 정의 Relationship Type은 Project가 아니라 World에 귀속된다.
2. Relationship Type 복구 시 기존 Role 및 Role-Category 매핑을 모두 폐기하고 새로 생성한다.

## 9.2 `relationship_roles`

Relationship 안에서 각 Document가 담당하는 Role을 정의한다.


## 9.3 `relationship_role_categories`

Relationship Role별 기본 허용 Category를 저장한다.

| 컬럼 | 타입 | Key | NULL | 설명 |
| --- | --- | --- | :---: | --- |
| `id` | BIGINT | PK | N | 매핑 ID |
| `relationshipRoleId` | BIGINT | FK → `relationship_roles.id` | N | Relationship Role |
| `categoryId` | BIGINT | FK → `categories.id` | N | 허용 Category |
| 공통 컬럼 | | | | |

### 제약

```text
UNIQUE(relationshipRoleId, categoryId)
```

`categoryId`는 1단계 Category만 허용한다.

### 허용 Category 범위

기본 Relationship Type의 기본 허용 Category는 기본 Category를 중심으로 구성한다.

World 사용자 정의 Relationship Type에서는 다음 Category를 선택할 수 있다.

1. 기본 Category.
2. 해당 World에 속한 모든 Project의 사용자 정의 Category.

사용자 정의 Category의 World는 다음 경로로 판정한다.

```text
category
→ project_categories
→ projects
→ worldId
```

하위 Category는 별도 매핑하지 않는다.

```text
인물 허용
→ 인물 > 인간 허용
→ 인물 > 인간 > 귀족 허용
```

# 11. 실제 Relationship

## 11.1 `relationships`

실제로 생성된 Relationship 인스턴스다.

Relationship은 Project가 아니라 World에 귀속된다.

| 컬럼 | 타입 | Key | NULL | 설명 |
| --- | --- | --- | :---: | --- |
| `id` | BIGINT | PK | N | Relationship ID |
| `worldId` | BIGINT | FK → `worlds.id` | N | 관계 소속 World |
| `relationshipTypeId` | BIGINT | FK → `relationship_types.id` | N | Relationship Type |
| 공통 컬럼 | | | | |

### 업무 규칙

기본 Relationship Type을 사용하는 경우:

```text
world_relationship_types
WHERE worldId = relationships.worldId
AND relationshipTypeId = relationships.relationshipTypeId
AND useYn = Y
AND delYn = N
```

이어야 한다.

사용자 정의 Relationship Type은:

```text
relationshipType.worldId
=
relationship.worldId
```

여야 한다.

`relationshipTypeId`는 Relationship 생성 후 변경할 수 없다.

다른 Relationship Type이 필요하면 기존 Relationship을 소프트 삭제하고 새 Relationship을 생성한다.

---

## 11.2 `relationship_targets`

실제 Relationship에 참여하는 Document와 Role을 연결한다.

| 컬럼 | 타입 | Key | NULL | 설명 |
| --- | --- | --- | :---: | --- |
| `id` | BIGINT | PK | N | 대상 매핑 ID |
| `relationshipId` | BIGINT | FK → `relationships.id` | N | Relationship |
| `relationshipRoleId` | BIGINT | FK → `relationship_roles.id` | N | Role |
| `documentId` | BIGINT | FK → `documents.id` | N | 대상 Document |
| 공통 컬럼 | | | | |

### 제약

```text
UNIQUE(relationshipId, relationshipRoleId)
```

Role 하나에는 Document 하나만 배정한다.

### 무결성

1. Role은 해당 Relationship Type에 속해야 한다.

```text
relationshipRole.relationshipTypeId
=
relationship.relationshipTypeId
```

2. 모든 대상 Document는 Relationship과 같은 World에 속해야 한다.

```text
document
→ project
→ worldId

=
relationships.worldId
```

3. 서로 다른 Project의 Document끼리 연결할 수 있다.
4. 별도 `projectId`를 `relationship_targets`에 저장하지 않는다.
5. 대상 Project는 `document → project` 경로로 판정한다.
6. `relationship_roles.requiredYn = Y`인 Role은 모두 존재해야 한다.
7. Relationship 대상은 기본적으로 2~4개다.
8. Document의 1단계 Category는 해당 Role의 최종 허용 Category에 포함되어야 한다.

# 15. 기본 데이터 정책

기본 데이터는 다음 세 종류다.

```text
기본 Category
기본 Template
기본 Relationship Type
```

기본 정의는:

```text
defaultYn = Y
```

이며 특정 Project나 World의 소유 데이터가 아니다.

세부 원칙은 다음과 같다.

1. 기본 Category는 모든 Project에서 직접 사용할 수 있다.
2. 기본 Category는 `project_categories`에 매핑하지 않는다.
3. 기본 Template은 시스템 전역에 존재한다.
4. 기본 Template을 특정 Project에 실제 적용할 때 `project_templates`를 사용한다.
5. 기본 Relationship Type은 `world_relationship_types`를 통해 World별 사용 여부를 관리한다.
6. 기본 정의 자체는 사용자에 의해 수정하거나 삭제하지 않는다.

# 16. 사용자 정의 데이터 정책

사용자 정의 데이터의 소속은 종류별로 다르다.

```text
사용자 정의 Category
→ Project 종속
→ project_categories로 소속 표현
```

```text
사용자 정의 Template
→ Project 종속
→ project_templates로 소속 표현
```

```text
사용자 정의 Relationship Type
→ World 종속
→ relationship_types.worldId
```

```text
실제 Relationship
→ World 종속
→ relationships.worldId
```

사용자 정의 Category와 Template은 다른 Project로 직접 이동시키지 않는다.

소속이나 계층 구조를 바꿔야 한다면 신규 데이터를 생성하고 필요한 Document 또는 적용 정보를 새 구조로 이동한다.

```text
SUPER_ADMIN

```

```text
→ 활성 project_admin_permissions가 있는 Project만 열람 가능

```

# 18. 변경 불가 데이터 정책

데이터 무결성을 위해 생성 후 변경하지 않는 항목을 명확히 한다.

## Category

```text
depth
parentId
```

생성 후 변경 불가.

계층 변경이 필요하면 신규 Category를 생성하고 기존 Document를 이동한다.

## Document

```text
title
```

생성 후 변경 불가.

제목은 Wiki Link 식별 문자열 역할을 한다.

## Relationship

```text
relationshipTypeId
```

생성 후 변경 불가.

다른 Relationship Type이 필요하면 기존 Relationship을 삭제하고 신규 Relationship을 생성한다.

---

# 19. 복구와 명시적 복원의 구분

동일명 생성 요청에 의한 복구와 사용자가 기존 데이터를 명시적으로 복원하는 행위는 구분한다.

```text
동일명 생성 요청에 의한 복구
→ 메인 row ID만 유지
→ 신규 요청값으로 초기화
→ 기존 연관 데이터 폐기
→ 신규 연관 데이터 생성
```

```text
명시적 복원
→ 해당 기능의 복원 정책에 따라 기존 상태를 되살릴 수 있음
```

Document Revision 복원은 대표적인 명시적 복원으로, 신규 Revision을 만들지 않고 `currentYn`을 전환한다.

# 20. 설계 요약

옴니노드의 데이터 경계는 다음 네 축으로 정리한다.

```text
System
→ 기본 정의 데이터
```

```text
World
→ ADMIN
→ 사용자 정의 Relationship Type
→ 실제 Relationship
```

```text
Project
→ 사용자 정의 Category
→ 사용자 정의 Template
→ Document
→ SUB_ADMIN 접근 권한
```

```text
Relationship
→ 같은 World의 여러 Project Document를 하나의 관계로 연결
```

20개 테이블 구조는 유지하며, 최신 정책에 따라 핵심적으로 다음을 변경한다.

1. `categories.worldId` 제거.
2. `project_categories`를 사용자 정의 Category의 Project 소속 매핑으로 재정의.
3. `templates.worldId` 제거.
4. `project_templates.categoryId`를 NULL 허용으로 변경.
5. `project_templates`를 Project-Template 소속 + 선택적 Category 적용 매핑으로 재정의.
6. `relationship_types.worldId`와 `relationships.worldId`는 유지.
7. 동일명 삭제 데이터 생성 요청은 메인 row만 초기화 복구하고 연관 데이터는 전부 폐기 후 재생성한다.
8. Category 계층, Document 제목, Relationship Type은 생성 후 불변으로 관리한다.
