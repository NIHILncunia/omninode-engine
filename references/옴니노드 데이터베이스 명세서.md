# 옴니노드 데이터베이스 명세서

## 1. 설계 개요

옴니노드는 하나의 설정 문서를 하나의 **노드(Node)** 로 취급하고, 문서를 작성·분류·연결하는 시스템이다.

핵심 기능은 다음 세 가지다.

```text
문서 관리
문서 분류
문서 연결
```

데이터의 주요 관리 범위는 다음과 같이 구분한다.

```text
World
├─ Project
│  ├─ Category 사용
│  ├─ Template 적용
│  └─ Document
│
├─ Admin
└─ Relationship
   └─ 같은 World의 여러 Project 문서를 연결
```

카테고리와 템플릿의 **정의**는 기본 데이터 또는 월드 사용자 정의 데이터로 존재하며, 실제 사용 구성은 프로젝트 단위로 결정한다.

관계 정의의 기본 데이터는 시스템 전역에 존재하고, 사용자 정의 관계 및 실제 관계 데이터는 월드 단위로 관리한다.

# 2. 공통 컬럼

모든 테이블은 다음 공통 컬럼을 가진다.

| 컬럼           | 타입                 | Key              | NULL | 설명              |
| ------------ | ------------------ | ---------------- | :--: | --------------- |
| `id`         | BIGINT             | PK               |   N  | 자동 증가 식별자       |
| `useYn`      | CHAR(1)            |                  |   N  | 사용 여부 `Y/N`     |
| `delYn`      | CHAR(1)            |                  |   N  | 소프트 삭제 여부 `Y/N` |
| `createId`   | BIGINT             | FK → `admins.id` |   Y  | 생성 관리자          |
| `createDate` | DATETIME/TIMESTAMP |                  |   N  | 생성 일시           |
| `updateId`   | BIGINT             | FK → `admins.id` |   Y  | 최종 수정 관리자       |
| `updateDate` | DATETIME/TIMESTAMP |                  |   Y  | 최종 수정 일시        |
| `deleteId`   | BIGINT             | FK → `admins.id` |   Y  | 삭제 관리자          |
| `deleteDate` | DATETIME/TIMESTAMP |                  |   Y  | 삭제 일시           |

날짜는 DB에서는 날짜/시간 타입으로 관리하고 API 입출력에서는 UTC ISO 8601 형식으로 통일한다.

```text
yyyy-MM-dd'T'HH:mm:ss.SSZ

예:
2026-08-18T01:04:32.15Z
```

상태의 의미는 다음과 같다.

```text
useYn = Y / delYn = N
→ 정상 사용

useYn = N / delYn = N
→ 존재하지만 비활성

delYn = Y
→ 소프트 삭제
```

상위 데이터가 비활성화되거나 삭제되어도 하위 데이터의 `useYn`, `delYn`을 연쇄 변경하지 않는다.

# 3. 관리자

## 3.1 `admins`

모든 관리자 계정을 관리한다.

SUPER_ADMIN, ADMIN, SUB_ADMIN은 별도 테이블을 만들지 않고 `role`로 구분한다.

| 컬럼                  | 타입                 | Key              | NULL | 설명               |
| ------------------- | ------------------ | ---------------- | :--: | ---------------- |
| `id`                | BIGINT             | PK               |   N  | 관리자 ID           |
| `email`             | VARCHAR            | UK               |   N  | 로그인 이메일          |
| `password`          | VARCHAR            |                  |   N  | 비밀번호 해시          |
| `name`              | VARCHAR            |                  |   N  | 관리자 이름           |
| `role`              | VARCHAR/ENUM       |                  |   N  | 관리자 역할           |
| `passwordChangedYn` | CHAR(1)            |                  |   N  | 최초 비밀번호 변경 완료 여부 |
| `useYn`             | CHAR(1)            |                  |   N  | 사용 여부            |
| `delYn`             | CHAR(1)            |                  |   N  | 삭제 여부            |
| `createId`          | BIGINT             | FK → `admins.id` |   Y  | 생성 관리자           |
| `createDate`        | DATETIME/TIMESTAMP |                  |   N  | 생성 일시            |
| `updateId`          | BIGINT             | FK → `admins.id` |   Y  | 수정 관리자           |
| `updateDate`        | DATETIME/TIMESTAMP |                  |   Y  | 수정 일시            |
| `deleteId`          | BIGINT             | FK → `admins.id` |   Y  | 삭제 관리자           |
| `deleteDate`        | DATETIME/TIMESTAMP |                  |   Y  | 삭제 일시            |

### `role`

```text
SUPER_ADMIN
ADMIN
SUB_ADMIN
```

### 제약 및 업무 규칙

```text
UNIQUE(email)
```

* SUPER_ADMIN은 시스템 전체에서 정확히 1명이다.
* SUPER_ADMIN은 모든 월드와 프로젝트에 접근할 수 있다.
* ADMIN은 SUPER_ADMIN의 승인으로 생성한다.
* SUB_ADMIN은 ADMIN이 직접 생성한다.
* ADMIN/SUB_ADMIN은 임시 비밀번호로 생성한다.
* ADMIN/SUB_ADMIN의 최초 `passwordChangedYn = N`.
* `passwordChangedYn = N`이면 비밀번호 변경 및 로그아웃 외 기능에 접근할 수 없다.
* 최초 비밀번호 변경 완료 시 `passwordChangedYn = Y`.
* SUPER_ADMIN은 최초부터 `passwordChangedYn = Y`로 관리한다.
* 삭제된 계정이라도 이메일은 재사용하지 않는다.

## 3.2 `admin_requests`

ADMIN 권한 신청을 관리한다.

| 컬럼           | 타입                 | Key              | NULL | 설명     |
| ------------ | ------------------ | ---------------- | :--: | ------ |
| `id`         | BIGINT             | PK               |   N  | 요청 ID  |
| `email`      | VARCHAR            |                  |   N  | 신청 이메일 |
| `name`       | VARCHAR            |                  |   N  | 신청자 이름 |
| `status`     | VARCHAR/ENUM       |                  |   N  | 처리 상태  |
| `useYn`      | CHAR(1)            |                  |   N  | 사용 여부  |
| `delYn`      | CHAR(1)            |                  |   N  | 삭제 여부  |
| `createId`   | BIGINT             | FK → `admins.id` |   Y  | 생성 관리자 |
| `createDate` | DATETIME/TIMESTAMP |                  |   N  | 신청 일시  |
| `updateId`   | BIGINT             | FK → `admins.id` |   Y  | 처리 관리자 |
| `updateDate` | DATETIME/TIMESTAMP |                  |   Y  | 처리 일시  |
| `deleteId`   | BIGINT             | FK → `admins.id` |   Y  | 삭제 관리자 |
| `deleteDate` | DATETIME/TIMESTAMP |                  |   Y  | 삭제 일시  |

### 상태

```text
PENDING
APPROVED
REJECTED
```

### 업무 규칙

* 동일 이메일의 과거 거절 요청은 존재할 수 있다.
* 동일 이메일에 활성 `PENDING` 요청이 두 개 이상 존재해서는 안 된다.
* 이미 `admins.email`에 존재하는 이메일은 ADMIN 신청을 할 수 없다.
* 승인 처리는 계정 생성과 요청 상태 변경을 하나의 트랜잭션으로 처리한다.

```text
PENDING
→ SUPER_ADMIN 승인
→ admins 생성(role = ADMIN)
→ 임시 비밀번호 생성
→ passwordChangedYn = N
→ APPROVED
→ 계정 정보 이메일 발송
```

| `createId`   | BIGINT             | FK → `admins.id` |   Y  | 생성 관리자 |
| `createDate` | DATETIME/TIMESTAMP |                  |   N  | 생성 일시  |

* ADMIN/SUB_ADMIN 구분은 `admins.role`로 판단한다.
* SUB_ADMIN은 여러 월드에 소속될 수 있다.

# 5. 카테고리

## 5.1 `categories`

카테고리 정의를 관리한다.

기본 제공 카테고리와 사용자 정의 카테고리를 동일 테이블에서 관리한다.

| 컬럼           | 타입                 | Key                  | NULL | 설명                |
| ------------ | ------------------ | -------------------- | :--: | ----------------- |
| `id`         | BIGINT             | PK                   |   N  | 카테고리 ID           |
| `worldId`    | BIGINT             | FK → `worlds.id`     |   Y  | 사용자 정의 카테고리 소속 월드 |
| `parentId`   | BIGINT             | FK → `categories.id` |   Y  | 상위 카테고리           |
| `name`       | VARCHAR            |                      |   N  | 카테고리명             |
| `depth`      | SMALLINT           |                      |   N  | 카테고리 단계 1~3       |
| `defaultYn`  | CHAR(1)            |                      |   N  | 기본 제공 여부          |
| `useYn`      | CHAR(1)            |                      |   N  | 전역/정의 사용 여부       |
| `delYn`      | CHAR(1)            |                      |   N  | 삭제 여부             |
| `createId`   | BIGINT             | FK → `admins.id`     |   Y  | 생성 관리자            |
| `createDate` | DATETIME/TIMESTAMP |                      |   N  | 생성 일시             |
| `updateId`   | BIGINT             | FK → `admins.id`     |   Y  | 수정 관리자            |
| `updateDate` | DATETIME/TIMESTAMP |                      |   Y  | 수정 일시             |
| `deleteId`   | BIGINT             | FK → `admins.id`     |   Y  | 삭제 관리자            |
| `deleteDate` | DATETIME/TIMESTAMP |                      |   Y  | 삭제 일시             |

### 기본/사용자 정의

```text
defaultYn = Y
→ worldId = NULL
→ 기본 제공
→ 수정/삭제 불가

defaultYn = N
→ worldId 필수
→ 월드 사용자 정의
```

### 트리 제약

```text
depth = 1
→ parentId = NULL

depth = 2
→ parentId 필수
→ parent.depth = 1

depth = 3
→ parentId 필수
→ parent.depth = 2
```

`depth`는 1~3만 허용한다.

### 사용자 정의 트리

사용자 정의 카테고리는 다음 아래에 생성할 수 있다.

```text
기본 카테고리
또는
같은 worldId의 사용자 정의 카테고리
```

다른 월드 사용자 정의 카테고리는 부모가 될 수 없다.

카테고리 자체에는 정렬 순서를 저장하지 않는다.


실제 사용 가능 여부는 모든 상위 경로가 활성 상태인지 함께 판단한다.

### 제목 제약

제목은 위키링크 식별 문자열 역할을 한다.

```text
[[문서 제목]]
```

따라서 생성 후 제목 수정은 허용하지 않는다.

활성 문서 기준:

```text
UNIQUE(projectId, title)
WHERE delYn = 'N'
```

### 카테고리 제약

```text
categoryId
→ depth = 1

subCategory1Id
→ NULL 가능
→ 값이 있으면 depth = 2
→ parentId = categoryId

subCategory2Id
→ NULL 가능
→ 값이 있으면 subCategory1Id 필수
→ depth = 3
→ parentId = subCategory1Id
```

선택된 모든 카테고리는 해당 프로젝트에서 사용 가능한 상태여야 한다.

* 문서 하나에는 현재 리비전이 정확히 하나 존재해야 한다.
* `content = ''`은 허용한다.
* `content = NULL`은 허용하지 않는다.

문서 생성:

```text
documents 생성
→ document_revisions 생성
→ currentYn = Y
```

수정:

```text
현재 content와 신규 content 비교
→ 동일: 리비전 생성 안 함
→ 다름: 기존 currentYn=N + 신규 revision currentYn=Y
```

복원:

```text
기존 currentYn = N
복원 대상 currentYn = Y
신규 리비전 생성 안 함
```

복원 후 수정하면 그때 신규 리비전을 생성한다.

| `createId`           | BIGINT             | FK → `admins.id`             |   Y  | 생성 관리자   |
| `createDate`         | DATETIME/TIMESTAMP |                              |   N  | 생성 일시    |
| `updateId`           | BIGINT             | FK → `admins.id`             |   Y  | 수정 관리자   |
| `updateDate`         | DATETIME/TIMESTAMP |                              |   Y  | 수정 일시    |
| `deleteId`           | BIGINT             | FK → `admins.id`             |   Y  | 삭제 관리자   |
| `deleteDate`         | DATETIME/TIMESTAMP |                              |   Y  | 삭제 일시    |

### 제약

```text
UNIQUE(relationshipId, relationshipRoleId)
```

역할 하나에는 문서 하나만 배정한다.

### 관계 무결성

역할은 해당 관계 유형에 속해야 한다.

```text
relationshipRole.relationshipTypeId
=
relationship.relationshipTypeId
```

대상 문서는 관계와 같은 월드에 속해야 한다.

```text
document
→ project
→ worldId

=
relationships.worldId
```

필수 역할:

```text
relationship_roles.requiredYn = Y
```

은 모두 존재해야 한다.

관계 대상은 기본적으로 2~4개다.

문서의 `categoryId`는 해당 역할의 허용 카테고리에 포함되어야 한다.

# 14. 기본 데이터 정책

기본 데이터는 다음 세 종류다.

```text
기본 카테고리
기본 템플릿
기본 관계
```

기본 정의는:

```text
defaultYn = Y
worldId = NULL
```

이다.

기본 정의 자체는 수정하거나 삭제하지 않는다.

프로젝트나 월드에서 필요하지 않을 경우 해당 매핑 테이블의 `useYn`을 변경한다.

```text
카테고리
→ project_categories.useYn

템플릿 적용
→ project_templates.useYn

기본 관계
→ world_relationship_types.useYn
```

# 15. 사용자 정의 데이터 정책

사용자 정의 카테고리·템플릿·관계는 월드에서 정의한다.

```text
defaultYn = N
worldId = 해당 월드
```

카테고리와 템플릿은 같은 월드 내 여러 프로젝트에서 재사용할 수 있다.

관계는 월드 전체 데이터이므로 프로젝트별로 분리하지 않는다.

```text
└─ 여러 Project
   └─ 여러 Document

같은 World의 Document라면
Project가 달라도 Relation으로 연결 가능
```
