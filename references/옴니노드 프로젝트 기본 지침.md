# 옴니노드 프로젝트 기본 지침

## 1. 프로젝트 정의

**옴니노드(Omninode)** 는 세계관의 설정 문서를 체계적으로 작성하고 관리하며, 각각의 설정 문서를 서로 연결하여 세계관을 더 깊고 입체적으로 구축하기 위한 ​**관계형 세계관 관리 시스템**이다.

옴니노드의 핵심은 개별 설정 문서를 단순히 보관하는 것이 아니라, 문서와 문서 사이의 의미 있는 관계를 데이터로 관리하는 것이다.

세계관을 구성하는 각각의 설정은 독립된 정보가 아니라 다른 설정과 연결되어 있으며, 옴니노드는 이러한 연결 자체를 세계관의 중요한 데이터로 취급한다.

---

# 2. 프로젝트의 목적

일반적인 세계관 관리 도구에서는 인물, 장소, 국가, 사건 등의 설정을 각각 작성할 수 있지만 설정 사이의 관계는 대부분 문서 본문이나 단순 링크에 의존한다.

옴니노드는 이러한 관계를 명시적인 데이터로 관리한다.

예:

- 인물 → 소속 → 세력
- 인물 → 출생지 → 지역
- 인물 → 부모 → 인물
- 인물 → 자녀 → 인물
- 국가 → 수도 → 도시
- 국가 → 적대 → 국가
- 사건 → 발생 장소 → 지역
- 사건 → 참여 → 인물
- 사건 → 원인 → 사건
- 사건 → 결과 → 사건
- 아이템 → 소유자 → 인물
- 인물 → 제작 → 아이템

이러한 관계들이 축적되면 단순한 설정 문서 모음을 넘어 **세계관 전체의 구조를 데이터로 표현할 수 있게 된다.**

---

# 3. 기본 계층 구조

옴니노드의 기본 구조는 다음과 같다.

```text
프로젝트
└─ 월드
   ├─ 카테고리
   │  ├─ 템플릿
   │  └─ 설정 문서
   │
   ├─ 문서 관계
   │
   └─ 관계 기반 표현
      ├─ 연표
      ├─ 가계도
      ├─ 인물 관계
      ├─ 사건 관계
      └─ 기타 특화 표현
```

각 단계는 명확한 역할을 가진다.

---

# 4. 프로젝트

**프로젝트(Project)** 는 옴니노드에서 가장 상위의 관리 단위이다.

하나의 프로젝트는 여러 개의 월드를 포함할 수 있다.

예:

```text
프로젝트: 프로젝트 위그드라실

├─ 룩스테라
├─ 마키나즈
└─ 기타 월드
```

프로젝트는 서로 관련된 여러 세계관을 하나의 작업 단위로 묶기 위한 컨테이너 역할을 한다.

---

# 5. 월드

**월드(World)** 는 실제 세계관 데이터가 관리되는 핵심 공간이다.

카테고리, 템플릿, 설정 문서 및 문서 관계는 기본적으로 월드를 기준으로 관리한다.

하나의 프로젝트 안에 여러 개의 독립적인 월드를 둘 수 있다.

---

# 6. 카테고리

**카테고리(Category)** 는 설정 문서의 종류와 분류 체계를 정의한다.

예:

```text
인물
지역
국가
도시
세력
종족
사건
아이템
능력
직업
문화
종교
```

카테고리는 계층 구조를 가질 수 있다.

예:

```text
지역
├─ 대륙
├─ 국가
├─ 도시
└─ 시설
```

카테고리 구조는 세계관마다 다를 수 있으므로 사용자가 직접 구성할 수 있어야 한다.

---

# 7. 템플릿

**템플릿(Template)** 은 특정 카테고리에 속하는 설정 문서가 어떤 데이터를 가지는지 정의한다.

예를 들어 `인물` 템플릿은 다음과 같은 항목을 가질 수 있다.

```text
이름
성별
종족
출생일
출생지
소속
직업
신장
외형
성격
설명
```

`국가` 템플릿은 다른 구조를 사용할 수 있다.

```text
국가명
수도
통치 체제
통치자
인구
종족 구성
종교
건국일
영토
설명
```

템플릿은 설정 문서의 **데이터 스키마** 역할을 한다.

---

# 8. 템플릿 필드

템플릿은 여러 개의 필드를 가진다.

기본적으로 다음과 같은 필드 타입을 고려한다.

- 단문 텍스트
- 장문 텍스트
- 숫자
- 날짜
- 참 / 거짓
- 단일 선택
- 다중 선택
- 이미지
- 파일
- URL
- 다른 설정 문서 참조
- 관계형 필드

필드 타입은 향후 추가할 수 있도록 확장 가능한 구조를 지향한다.

---

# 9. 설정 문서

**설정 문서(Document)** 는 세계관을 구성하는 실제 정보 단위이다.

예:

```text
인물
- 아미유
- 하티 크레실크

국가
- 에테르나크
- 하르카둠

지역
- 에리디안
- 라크샤라

사건
- 에리디안 전쟁
- 라크샤라 침공
```

설정 문서는 자신이 속한 템플릿에서 정의한 구조화 데이터와 자유로운 본문을 함께 가질 수 있다.

즉 하나의 문서는 다음 두 가지 정보를 동시에 가질 수 있다.

```text
구조화 데이터
+
서술형 설정 문서
```

---

# 10. 문서 관계

**문서 관계(Document Relation)** 는 옴니노드의 핵심 기능이다.

하나의 설정 문서는 다른 설정 문서와 연결될 수 있다.

단순한 링크가 아니라 **관계의 의미를 함께 저장한다.**

예:

```text
아미유
 ├─ 출생지 → 청연
 ├─ 소속 → 특정 세력
 ├─ 참여 → 사건 A
 └─ 소유 → 아이템 B
```

관계는 세계관 구조를 표현하는 데이터로 취급한다.

---

# 11. 관계 타입

관계에는 의미를 나타내는 **관계 타입(Relation Type)** 이 존재한다.

예:

```text
소속
소유
제작
거주
출생
참여
지배
동맹
적대
부모
자녀
배우자
스승
제자
선행
후행
원인
결과
발생
```

사용자는 월드에 필요한 관계 타입을 정의할 수 있어야 한다.

관계 타입에 따라 연결 가능한 문서 종류를 제한하는 기능도 고려한다.

예:

```text
부모

출발: 인물
도착: 인물
```

```text
수도

출발: 국가
도착: 도시
```

---

# 12. 관계 저장과 관계 표현의 분리

옴니노드에서는 **관계 저장**과 **관계 표현**을 구분한다.

문서 관계를 저장했다고 해서 모든 관계를 시각적으로 표현할 필요는 없다.

관계는 기본적으로 세계관 데이터의 일부로 저장한다.

그리고 해당 관계를 구조적으로 표현하는 것이 실제로 유용한 경우에만 별도의 표현 기능을 사용한다.

---

# 13. 관계 기반 표현

관계 기반 표현은 독립적인 데이터를 다시 입력하는 기능이 아니다.

기존 설정 문서와 문서 관계를 읽어서 특정 목적에 맞는 형태로 보여주는 기능이다.

대표적인 예시는 다음과 같다.

- 연표
- 가계도
- 인물 관계
- 사건 관계
- 향후 추가되는 특화 표현

---

# 14. 연표

사건 문서에는 날짜나 시점 정보를 둘 수 있다.

사건 문서는 다른 사건과 선행, 후행, 원인, 결과 등의 관계를 가질 수 있다.

예:

```text
사건 A
↓
사건 B
↓
사건 C
```

각 사건의 발생 시점과 관계 데이터를 이용하면 세계관의 연표를 구성할 수 있다.

단순한 날짜순 정렬뿐만 아니라 다음과 같은 정보까지 함께 표현할 수 있다.

- 사건의 선행 관계
- 사건의 후속 관계
- 사건의 원인
- 사건의 결과
- 관련 인물
- 관련 지역
- 관련 세력

연표는 별개의 사건 데이터를 다시 입력하는 기능이 아니라 기존 사건 문서를 활용한다.

---

# 15. 가계도

인물 사이의 가족 관계를 연결하면 가계도를 구성할 수 있다.

예:

```text
인물 A
├─ 자녀 → 인물 B
└─ 자녀 → 인물 C
```

가계도에서 사용할 수 있는 관계 예시는 다음과 같다.

- 부모
- 자녀
- 배우자
- 형제자매
- 입양
- 혈통

기존 인물 문서와 가족 관계를 이용하는 것이 원칙이다.

가계도를 위해 별도의 인물 데이터를 다시 생성하지 않는다.

---

# 16. 인물 관계

인물 사이의 관계가 중요한 경우 해당 인물들을 중심으로 관계 구조를 표현할 수 있다.

예:

- 가족
- 친구
- 동료
- 연인
- 적대
- 경쟁
- 스승과 제자
- 주종
- 상관과 부하
- 소속 관계

인물 관계 표현 역시 기존 인물 문서와 문서 관계를 사용한다.

모든 인물 문서를 자동으로 관계도로 표현하는 것은 아니다.

필요한 범위와 목적을 지정하여 표현한다.

---

# 17. 사건 관계

사건 사이의 인과관계나 전개 구조가 중요한 경우 사건 관계를 표현할 수 있다.

예:

```text
사건 A
  ↓ 원인
사건 B
  ├─ 결과 → 사건 C
  └─ 결과 → 사건 D
```

사건 관계에는 다음과 같은 관계가 활용될 수 있다.

- 선행
- 후행
- 원인
- 결과
- 분기
- 연쇄
- 연관
- 동일 사건군

사건 관계 기능은 단순한 연표와는 목적이 다를 수 있다.

연표가 시간 순서를 중심으로 본다면 사건 관계는 사건 사이의 인과와 구조를 중심으로 본다.

---

# 18. 범용 관계 그래프는 기본 기능으로 두지 않는다

옴니노드는 모든 문서를 하나의 거대한 관계 그래프로 표현하는 것을 목표로 하지 않는다.

다음과 같은 기능은 기본 목표에서 제외한다.

- 전체 월드 자동 관계 그래프
- 모든 문서 자동 그래프화
- 모든 관계의 강제 시각화
- 범용 Graph View

관계 표현은 반드시 명확한 목적이 있을 때에만 제공한다.

즉, **관계가 존재한다는 것과 관계를 시각화한다는 것은 별개의 문제로 취급한다.**

---

# 19. 단일 데이터 원칙

동일한 정보를 표현하기 위해 별도의 데이터를 중복해서 만들지 않는다.

예를 들어 가계도를 만들기 위해 별도의 가계도 전용 인물 정보를 입력하지 않는다.

연표를 만들기 위해 별도의 사건 정보를 다시 작성하지 않는다.

인물 관계를 만들기 위해 별도의 관계용 인물 데이터를 만들지 않는다.

기존 설정 문서와 문서 관계를 그대로 사용한다.

즉,

**한 번 작성한 설정 데이터를 여러 기능에서 재사용하는 구조**

를 지향한다.

---

# 20. 문서 탐색

사용자는 다양한 방식으로 세계관을 탐색할 수 있어야 한다.

기본적인 탐색 방식은 다음과 같다.

- 프로젝트별
- 월드별
- 카테고리별
- 문서별
- 관계별
- 검색
- 연결된 문서

하나의 문서를 열었을 때 해당 문서와 연결된 다른 문서를 자연스럽게 탐색할 수 있어야 한다.

---

# 21. 검색

세계관 데이터가 증가하는 것을 전제로 검색 기능을 설계한다.

기본적으로 다음 검색을 고려한다.

- 문서 제목 검색
- 문서 본문 검색
- 템플릿 필드 검색
- 카테고리 검색
- 관계 검색
- 월드 전체 검색

---

# 22. 1차 개발 목표

위키 엔진과 본격적인 협업 기능은 1차 범위에서 제외한다.

# 24. 1차 관계 기반 표현

1차 버전에서는 관계 데이터 저장 구조를 우선적으로 완성한다.

관계 기반 표현 기능은 핵심 기능의 안정성을 해치지 않는 범위에서 단계적으로 추가한다.

우선 고려 대상은 다음과 같다.

- 연표
- 가계도
- 인물 관계
- 사건 관계

이 기능들은 관계 시스템 위에서 동작하는 부가 표현 기능으로 취급한다.

---

# 25. 1차에서 제외할 기능

다음 기능은 구조상 고려할 수 있으나 실제 1차 구현 범위에서는 제외한다.

- 문서 Revision
- 문서 변경 이력
- 문서 변경 비교
- 과거 Revision 복원
- 사용자별 변경 기록
- 문서 토론
- 토론 스레드
- 편집 승인
- 복잡한 권한 관리
- 실시간 공동 편집

이 기능들은 후속 **위키 엔진 단계**에서 구현한다.

---

# 26. 위키 엔진

옴니노드의 최종 단계에서는 세계관 데이터 관리 시스템 위에 **위키 엔진**을 결합한다.

각 설정 문서는 위키 문서처럼 관리할 수 있어야 한다.

위키 엔진의 핵심 목표는 다음과 같다.

- 모든 문서의 변경 기록 관리
- 변경 전후 비교
- 과거 문서 복원
- 수정 주체 추적
- 문서별 토론
- 편집 과정 추적

---

# 27. 문서 리비전

모든 문서의 변경 사항을 **Revision** 단위로 저장한다.

사용자는 다음 정보를 확인할 수 있어야 한다.

- 누가 수정했는가
- 언제 수정했는가
- 무엇을 수정했는가
- 이전 내용은 무엇인가
- 현재 내용은 무엇인가

과거 Revision으로 문서를 복원할 수도 있어야 한다.

---

# 28. 구조화 데이터의 리비전

Revision은 문서 본문만을 대상으로 하지 않는다.

템플릿 기반 구조화 데이터의 변경도 추적해야 한다.

예:

```text
소속

기존: 세력 A
변경: 세력 B
```

또는:

```text
출생지

기존: 지역 A
변경: 지역 B
```

---

# 29. 관계 리비전

최종적으로는 문서 관계의 변경 역시 이력 관리 대상으로 확장할 수 있다.

예:

```text
관계 추가
인물 A → 소속 → 세력 B
```

```text
관계 삭제
인물 A → 적대 → 인물 C
```

이를 통해 세계관의 설정 구조가 언제 어떻게 변경되었는지 추적할 수 있다.

---

# 30. 변경 비교

Revision 사이의 차이를 비교할 수 있어야 한다.

비교 대상은 다음과 같다.

- 문서 본문
- 템플릿 필드 값
- 메타데이터
- 관계
- 향후 필요한 기타 데이터

사용자가 변경 내용을 직관적으로 확인할 수 있는 Diff 기능을 제공하는 것을 목표로 한다.

---

# 31. 롤백

과거 Revision으로 문서를 복원할 수 있어야 한다.

롤백은 과거 Revision을 현재 문서로 덮어쓰는 방식보다 새로운 Revision을 생성하는 방식이 바람직하다.

이를 통해 복원 행위 자체도 기록으로 남길 수 있다.

---

# 32. 문서 토론

각 설정 문서는 독립적인 토론 공간을 가질 수 있어야 한다.

문서 내용에 대한 논의가 필요한 경우 문서를 즉시 수정하기 전에 토론할 수 있다.

예:

```text
문서: 에테르나크

토론
├─ 건국 연도 변경 제안
├─ 마황제 설정 충돌
└─ 주변 국가 관계 수정
```

토론은 단순 댓글 기능에 그치지 않는다.

해당 설정이 어떤 논의를 거쳐 현재 상태에 도달했는지 확인할 수 있는 기록 기능으로 발전시킨다.

---

# 33. 최종 구조

옴니노드의 최종적인 개념 구조는 다음과 같다.

```text
프로젝트
│
├─ 월드
│  │
│  ├─ 카테고리
│  │  │
│  │  ├─ 템플릿
│  │  └─ 설정 문서
│  │
│  ├─ 문서 관계
│  │
│  └─ 관계 기반 표현
│     ├─ 연표
│     ├─ 가계도
│     ├─ 인물 관계
│     ├─ 사건 관계
│     └─ 기타 특화 표현
│
└─ 위키 엔진
   ├─ Revision
   ├─ 변경 이력
   ├─ Diff
   ├─ Rollback
   └─ 문서 토론
```

# 34. 핵심 원칙

## 원칙 1. 문서는 세계관의 기본 단위이다.

세계관의 실제 설정은 설정 문서로 관리한다.

---

## 원칙 2. 문서와 문서 사이의 관계 역시 세계관의 데이터이다.

관계를 단순 링크가 아니라 의미 있는 구조 데이터로 취급한다.

---

## 원칙 3. 관계 저장과 관계 표현을 구분한다.

관계가 존재한다고 해서 반드시 시각화하지 않는다.

---

## 원칙 4. 관계 표현은 목적이 있을 때만 사용한다.

연표, 가계도, 인물 관계, 사건 관계처럼 실제로 구조적인 표현이 유용한 경우에만 제공한다.

---

## 원칙 5. 동일한 설정을 기능별로 중복 입력하지 않는다.

기존 문서와 관계를 재사용한다.

---

## 원칙 6. 세계관 구조는 사용자가 정의한다.

카테고리와 템플릿은 고정하지 않는다.

---

## 원칙 7. 관계 기반 기능은 원본 데이터를 변경하지 않는다.

연표나 가계도 등은 문서와 관계 데이터를 읽어 표현하는 기능이다.

---

## 원칙 8. 1차 개발에서는 핵심 기능에 집중한다.

프로젝트, 월드, 카테고리, 템플릿, 설정 문서, 관계 시스템을 우선 구현한다.

위키 엔진은 이후 단계에서 추가한다.

---

# 35. 1차 개발의 한 문장 정의

**사용자가 프로젝트와 월드를 만들고, 카테고리와 템플릿을 정의한 뒤 설정 문서를 작성하고 서로 연결할 수 있는 세계관 관리 시스템을 완성한다.**

---

# 36. 옴니노드의 한 문장 정의

**옴니노드는 세계관의 설정 문서를 구조화하고 서로 연결하여, 필요한 경우 그 관계로부터 연표·가계도·인물 관계·사건 관계 등 더 깊은 세계관 구조를 만들어내는 관계형 세계관 관리 시스템이다.**

---

# 37. 최종 목표

옴니노드의 최종 목표는 단순한 설정 문서 관리 프로그램이 아니다.

세계관의 모든 설정 문서와 문서 사이의 관계를 체계적으로 관리하고, 필요한 영역에서는 그 관계를 구조적으로 표현하며, 모든 변경 과정과 논의까지 추적할 수 있는 **세계관 특화 위키 시스템**을 구축하는 것이 최종 목적이다.
